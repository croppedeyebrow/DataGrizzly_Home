# 12. DB 제약·보존·마이그레이션

> v5.0 기준: [[SCOPE_v5]] 적용. 주력 Kotlin·Rust·TypeScript·PostgreSQL. LLM·C++ 제외, Go는 국소 배포 도구로 필요할 때만 사용합니다. 로컬 자원은 [[02_RESOURCE_BUDGET]] 참조.
복구 가능한 원본과 명시적인 관계

## 키와 제약

Entry ID는 불변, slug는 종류별 유일성을 갖습니다. Revision은 entry_id+revision_no 유일, 발행 요청 키도 유일합니다. ProjectLog는 entry_id를 PK/FK로 두고 project_id·order_key를 가집니다. SiteReleaseItem은 release_id+entry_id와 revision_id를 연결합니다.

## 관계·인덱스

EntryTaxonomy, SeriesItem, EntryRelation, RevisionMedia로 다대다를 표현합니다. 작업 조회용 status+next_attempt_at, 과정 목록용 project_id+order_key, 수정 이력용 entry_id+revision_no 인덱스를 둡니다. 실제 쿼리로 실행 계획을 확인합니다.

## 변경 정책

본문·제목·메타 수정은 Revision으로 보존합니다. 초안 버전 검사로 갱신 충돌을 막습니다. 검증 상태는 발행 상태와 별개입니다. 삭제는 우선 보관/철회로 처리하고, 영구 삭제는 첨부·수정본 참조를 확인합니다.

## 마이그레이션

버전 관리 도구로 스키마를 순서대로 변경합니다. 컬럼 추가 → 호환 코드 배포 → 데이터 변환 → 오래된 컬럼 제거 순서를 기본으로 합니다. API 이미지 복귀와 DB 복원은 다른 작업이며 파괴적 변경의 자동 롤백을 가정하지 않습니다.

## 백업 목표안

일 1회 DB와 첨부 매핑을 외부 저장소에 백업하고 7개 일간·4개 주간 보관을 초기 정책으로 제안합니다. 목표 RPO 24시간/RTO 4시간은 복원 실습으로 검증할 목표입니다. 이후 발행 빈도·유실 허용량에 따라 조정합니다.
