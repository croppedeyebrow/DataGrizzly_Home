## 작업 시작 전 확인

1. [초기 시작 규칙](../00_guide/ZERO_START.md)과 [명령 계약](../00_guide/COMMANDS.md)을 읽습니다.
2. 작업 위치는 저장소 루트입니다. 아래 경로는 모두 저장소 루트 기준 제안이며 기존 코드가 있으면 대응 경로를 기록하고 재사용합니다.
3. 선행 태스크 완료 기록과 실제 파일/테스트 결과를 확인합니다. 문서의 체크만으로 완료를 추정하지 않습니다.
4. 이번 태스크에 필요한 연결 기능 명세와 API/schema 계약을 읽고 변경될 필드를 먼저 적습니다.

## 생성·수정할 산출물

`services/cms/publication/releases/**; discovery/denylist/**`

파일명이 아직 없으면 해당 책임에 맞는 파일을 만듭니다. 경로를 변경하면 관련 명령과 연결 문서도 함께 고칩니다. 여러 파일을 한 파일로 억지로 합치지 않습니다.

## 세부 구현 작업

### M3-03.01 — 세대 단조 증가

- **할 일:** 사이트별 활성화 직렬화와 release sequence 비교를 구현합니다. 오래된 작업의 성공 통지는 무시/거부합니다.
- **단계 완료 결과:** 최신본을 예전 작업이 덮지 못함
- **기록:** 변경 파일과 이 조건을 확인한 명령/관측값을 작업 기록에 남깁니다.

### M3-03.02 — 철회 먼저 차단

- **할 일:** Entry denylist를 영속 저장하고 검색/질문/공개 API에서 즉시 적용합니다.
- **단계 완료 결과:** 검색 인덱스 재빌드 전에도 차단
- **기록:** 변경 파일과 이 조건을 확인한 명령/관측값을 작업 기록에 남깁니다.

### M3-03.03 — 정적·첨부 회수

- **할 일:** 현재와 이전 release의 해당 HTML·첨부 접근 정책을 점검하고 CDN purge/삭제를 추적합니다. origin release URL을 통한 우회 접근도 정책에 포함합니다.
- **단계 완료 결과:** 외부 캐시 한계와 실제 완료 범위를 표시
- **기록:** 변경 파일과 이 조건을 확인한 명령/관측값을 작업 기록에 남깁니다.

### M3-03.04 — 복귀 필터

- **할 일:** 과거 release로 복귀할 때 이후 철회 목록을 그대로 적용합니다. static 호스팅이 이를 즉시 적용 못하면 안전한 재빌드 또는 접근 차단이 끝날 때까지 복귀를 보류합니다.
- **단계 완료 결과:** 과거 release 재활성화로 철회 글 재노출 금지
- **기록:** 변경 파일과 이 조건을 확인한 명령/관측값을 작업 기록에 남깁니다.

### M3-03.05 — 운영 재시도

- **할 일:** purge 일부 실패를 별도 상태로 유지하고 retry합니다. 작업 성공과 외부 캐시 회수 보장을 구분합니다.
- **단계 완료 결과:** 철회 작업의 미완료 항목이 보임
- **기록:** 변경 파일과 이 조건을 확인한 명령/관측값을 작업 기록에 남깁니다.

## 입력·오류·경계 검증

역순 배포완료, CDN purge 실패, 이전release origin 접근, 철회후 rollback, 첨부 직접URL을 확인합니다.

정상 케이스만 확인하지 않습니다. 입력이 잘못된 경우, 선행 자원이 없는 경우, 관련 외부 컴포넌트가 실패한 경우를 구분합니다. 실제 실패 주입이 불가능하면 미실행으로 적고 실행 환경을 명시합니다.

## 실행 방법과 증거

[명령 계약](../00_guide/COMMANDS.md)의 해당 구성요소 검사부터 실행합니다. 기능 테스트가 아직 없으면 이 태스크의 위험을 검증하는 테스트를 작성한 뒤 실제 명령을 기록합니다. 빌드 성공은 기능 수용조건 충족과 별개입니다.

| 검증 구분 | 확인 대상 | 남길 증거 |
|---|---|---|
| 계약 | 연결 기능 명세·schema·API 응답 | 입력/응답 예제, schema 검증 결과 |
| 정상 동작 | 위 세부 작업의 완료 결과 | 테스트 이름·실행 명령·결과 |
| 실패 동작 | 위 경계·오류 시나리오 | 재현 절차·오류코드·상태 보존 결과 |
| 회귀 | 영향을 받은 기존 공개/관리 흐름 | 관련 테스트 결과·변경 전후 차이 |

## 실패 시 복구·중단 기준

- 파일/명령 없음: 아직 산출물을 생성하지 않았는지 먼저 확인합니다. 가짜 성공 스크립트로 통과시키지 않습니다.
- 계약과 코드 불일치: producer/consumer/fixture를 함께 검토하고 schemaVersion 변경 필요성을 기록합니다.
- 데이터 변경 실패: 트랜잭션·migration 이력을 확인합니다. 개발 DB 전체 삭제를 기본 해결법으로 쓰지 않습니다.
- 선행 태스크 결함: 해당 ID와 재현 증거를 남기고 현재 작업 완료를 보류합니다.
- 리소스 부족: 측정값을 남기고 선택 기능을 비활성화합니다. 승인되지 않은 유료 자원을 자동 생성하지 않습니다.

## 범위 제한

이 작업에 필요한 기능과 검증만 구현합니다. P2 기능을 P0/P1의 필수 의존성으로 추가하지 않습니다. 새 서비스·DB·언어·호스팅을 임의 도입하지 않습니다. 기존 사용자 변경은 보존합니다.
