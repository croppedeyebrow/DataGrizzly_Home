# S21 체크포인트·권한·환경값 준비

상태: `feat/s21-checkpoint`에 `workflow` 스키마와 런타임 계정을 넣었다. 문서 워크플로 구현은 아니다. 선행: [[S20]], PostgreSQL 개발 인스턴스. [[WF04_DATA_API]]

1. 워커 전용 DB 사용자와 checkpoint schema 또는 별도 DB를 설계합니다. CMS 테이블 쓰기 권한이 없어야 합니다.
2. workers/document-workflow에서 `uv add langgraph-checkpoint-postgres "psycopg[binary,pool]"`를 수행하고 버전 호환·lock diff를 확인합니다.
3. .env.example에는 CMS_INTERNAL_BASE_URL, WORKFLOW_CHECKPOINT_DSN, WORKFLOW_TOKEN, WORKFLOW_VERSION, WORKFLOW_MAX_JOBS=1을 이름/예시로만 작성합니다. 실제 secret은 .env 또는 환경으로 주입하며 자동 .env 로딩을 구현했는지 확인합니다.
4. 버전별 공식 API에 맞춰 checkpointer setup 전용 명령을 만듭니다. 관리 migration 계정과 런타임 계정을 구분하고 setup은 임의 매 실행마다 수행하지 않습니다.
5. 단순 state의 값을 저장하는 graph를 한 번 실행하고 프로세스를 완전히 종료합니다. 같은 thread_id로 새 프로세스에서 읽어 persistence를 확인합니다.
6. 다른 schema의 CMS 테이블 수정 시도가 권한 오류인지 확인합니다. 로그에서 DSN 암호·토큰을 마스킹합니다.

완료 조건: 재시작 복구 증거, 최소 권한 검사, schema/DB 격리 기록, setup 재실행의 안전성, backup 대상 등록. 실패 시 DB 전체 삭제 대신 신규 schema만 검토하며 기존 CMS 데이터를 보존합니다.

## 작업 완료 기록

- 작업 브랜치/커밋: `feat/s21-checkpoint`. 커밋은 하지 않았다.
- 패키지: `langgraph-checkpoint-postgres` 3.2.1, `psycopg` 3.3.9. C: 여유는 17.58 GiB에서 16.55 GiB가 되었다.
- 저장 위치: 데이터베이스 `datagrizzly`의 `workflow` 스키마. 런타임 계정은 `workflow_runtime`이고 CMS 테이블 권한은 없다. `datagrizzly`는 지우지 않았다.
- 환경값: `.env` 자동 로딩은 넣지 않았다. 이름 예시는 `.env.example`에 있다. 확인에 쓴 런타임 비밀번호는 그 프로세스 환경에만 있었고 `.env`에는 남기지 않았다. `WORKFLOW_RUNTIME_PASSWORD`를 지정하고 `setup-checkpoint`를 다시 실행하면 계정 비밀번호가 바뀐다.
- 확인: `uv run pytest` 6 passed. `setup-checkpoint`를 두 번 실행해도 `workflow` 스키마만 유지됐다. `checkpoint-write` 프로세스가 끝난 뒤 새 프로세스의 `checkpoint-read`가 `checkpoint-ok`를 읽었다. `checkpoint-probe-cms`는 `insufficient_privilege`다.
- 백업 대상: `workflow_checkpoint`.
- 다음 작업: S22. 문서 워크플로 구현 완료로 표시하지 않는다.
